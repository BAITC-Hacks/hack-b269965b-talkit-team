# Фаза 5 — оценка и исправления

## Задание

1. Запусти полный router-only live-eval исходных 104 реплик с изолированным контекстом. Сохрани predictions.json, исходный вывод evaluate.py, model ID, commit, параметры и версию/хеш промпта. Не меняй evaluator или expected ради роста результата. Не пропускай ошибки API из отчёта; они не равны правильным ответам.
2. По каждому промаху выпиши ожидаемый/фактический маршрут и причину ошибки. Исправляй общие правила description/not_this_if, multi-intent, системные намерения и обработку языка, не добавляй таблицу «тестовая фраза → ответ». Не заявляй результат на скрытом наборе по dev-eval.
3. Пройди 10 dialogs_sample как последовательности. В runtime поступают только реплики клиента и доступный ему контекст; ожидаемые scenarios/slots/actions используются проверяющим кодом. Проверяй полученные действия, preview/execute, перенесённый контекст и содержание ответа, а не только полное совпадение текста бота.
4. Добавь unit/integration-регрессии: несколько намерений; urgent первым; «нет» отменяет; «да, но…» не подтверждает автоматически; повтор execute; смена параметров после preview; неизвестный номер; несколько полисов; возврат к теме; ошибка tool arguments; новый ход во время прошлого; поздний Yandex final/refinement; один STT недоступен; TTS ошибка и остановка; изоляция сессий.
5. Запиши новые добровольные тестовые фразы команды: русский, казахский, смешанная речь, телефон/номер, короткое согласие/отказ, запрос оператора. Не использовать записи реальных клиентов. Голосовой smoke нужен отдельно: текстовый eval не проверяет DSR, микрофон, TTS или полную задержку.
6. При исправном основном решении сравни OpenAI-only, Yandex-only и DSR на одинаковых записях команды. Сравни корректность намерений и критичных слотов, долю уточнений и реальную latency. Это диагностическое сравнение, не доказательство превосходства без достаточных данных. Не расходуй последние часы на формальный STT-бенчмарк.
7. Оптимизируй только замеренные проблемы: повторная загрузка каталога, ненужные LLM-вызовы, новая сессия на каждый ход, дублированные токены, чрезмерное ожидание STT, длинный текст ответа. Не меняй модель/протокол/архитектуру без конкретной измеренной причины и повторной проверки.

## Проверка

Есть реальные отчёты, перечень исправленных общих ошибок и отдельно оставшиеся ограничения. Все обязательные классы покрыты тестами. Ни один тест не утверждает, что внешний провайдер проверен, если использовался fake. UI работает после исправлений.
