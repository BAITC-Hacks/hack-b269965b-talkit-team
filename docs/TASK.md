## 2. Итоговый продукт [КЕЙС]

**Одна веб-страница голосового симулятора с двумя представлениями:** клиент разговаривает с оператором, супервизор видит обработку того же разговора.

Пользователь говорит произвольную фразу в микрофон на русском или казахском, в том числе смешивает языки. Система понимает запрос, выбирает подходящий сценарий, использует предоставленные данные, уточняет необходимое, отвечает голосом и показывает, почему приняла решение. При смене темы разговор не должен сводиться к повторному старту без контекста.

LLM используется **в точке содержательного выбора**, а не только для перефразирования решения старого intent-классификатора. Главный предмет оценки — качество маршрутизации, не соревнование речевых моделей. DSR помогает правильно услышать запрос, но не заменяет новый LLM-router.

**Не разрабатываем Career Quest, HR-навигацию и рейтинги сотрудников.** Это другой кейс исходного задания.

```ts
  slots: Record<string, unknown>;
  is_continuation: boolean;
};
```

Массив `scenarios` обязателен: запрос может содержать несколько намерений. Единственное поле `scenarioId` недостаточно. Сервер проверяет форму, диапазоны и разрешённые ID по каталогу; модельный вывод не является исполняемой командой сам по себе.

В промпте использовать `description`, `not_this_if`, приоритет и репрезентативные примеры каталога. Не выбрасывать границы соседних сценариев. Не передавать в промпт `expected`, эталонные ответы оценивания и будущие реплики диалога.

Особые случаи:

- `SYS_OUT_OF_SCOPE`: запрос не относится к услугам Saqta.
- `SYS_UNCLEAR`: информации недостаточно, нужен один уточняющий вопрос.
- `SYS_GOODBYE`: завершение разговора.
- Среди нескольких намерений сначала обрабатывается `urgent`, остальные — в порядке упоминания. Не вводить самовольно сортировку всех `high` перед `normal`.
- Срочные сценарии каталога: `SC11`, `SC15`, `SC38`; решение принимается по смыслу и границам сценария, не по одному ключевому слову.

### 4.2. Неуверенность [референсная политика КИТ]

README предлагает:

- `confidence ≥ 0.75` — запуск сценария;
- `0.45–0.75` — уточнение через `SYS_UNCLEAR` с двумя вероятными вариантами;
- `< 0.45` два раза подряд либо явная просьба клиента — передача оператору с контекстом.

[КОМАНДА] В коде устранить пересечение границы явно: `>= 0.75`, затем `>= 0.45 && < 0.75`, затем `< 0.45`. При первом низком результате — уточнение; после двух подряд — handoff. Это реализация референсной политики, а не доказательство калиброванной вероятности ошибки. Некорректный JSON, неизвестный ID и отказ модели не превращать в фиктивно уверенный маршрут.

Короткое обоснование объясняет смысловой признак решения. Не требовать и не показывать скрытые рассуждения модели; достаточно проверяемой причины, например «клиент оспаривает размер выплаты, а не спрашивает её статус».

### 4.3. Состояние разговора [КИТ + КОМАНДА]

Сохранять `sessionId`, `turnId`, язык ответа, идентифицированного клиента, активный сценарий, слоты, незавершённые намерения, прерванную тему, ожидаемый вопрос и ожидаемое подтверждение.

Не превращать каждый ответ с номером телефона или словом «да» в новый независимый бизнес-запрос. Однозначное продолжение заполняет ожидаемый слот; содержательная смена темы снова проходит LLM-выбор. Продолжение и смену темы нельзя различать только по наличию активного сценария.

При нескольких просьбах подтвердить, что оставшиеся вопросы сохранены, и после первого перейти к следующему. При смене темы сохранить незавершённое состояние и предложить вернуться. Текстовый и голосовой каналы используют один `handleTurn()` и одинаковые правила.

**Разделение источников:** в ТЗ возврат к прерванной теме и извлечение слотов перечислены среди опций; референсный kit подробно описывает их, а команда включает их в целевой MVP. Не выдавать все расширения kit за отдельные обязательные пункты таблицы Must-have ТЗ.

## 5. Действия, идентификация и ответы [КИТ + КОМАНДА]

Реализовать общий исполнитель, а не 40 отдельных LLM-агентов:

```text
Выбран сценарий
→ идентификация, если нужна
→ заполнение недостающих параметров
→ подготовка действия
→ подтверждение, если требуется
→ исполнение mock-действия
→ ответ по фактам / завершение / следующий вопрос / оператор
```

Требования к исполнителю:

1. Идентифицировать клиента по предоставленному идентификатору и использовать его записи. Для скрытого набора README прямо указывает поиск персонажей по телефону. Не выбирать клиента по похожему сценарию или знанию эталонного `client_id` из теста.
2. Реализовать действия по `actions.json` на данных `mock_backend.json` и `knowledge_base.json`. Расчёты выполнять кодом по формулам набора; не просить LLM придумать цену.
3. Не запускать весь массив `scenario.actions` на каждой реплике. Вызывать только действие, для которого готовы параметры и наступил нужный этап.
4. Соблюдать контракт ошибок, включая `{"error":{"code":"not_found","message":"..."}}`. При неизвестном телефоне переспросить один раз, затем предложить другой идентификатор или оператора — согласно kit.
5. Создавать новые ID без коллизий. Изменения выполнять в изолированном состоянии демо-сессии; исходные JSON оставлять неизменными.
6. Не отдавать весь backend в браузер и не подмешивать записи других клиентов в ответ. Передавать только необходимый контекст и результаты найденных записей.
7. Различать найденный факт, результат действия, отсутствие данных и отказ внешнего сервиса. Не говорить «оформлено» или «отправлено», если действие не выполнено.

### Подтверждение — проверка кода, не обещание модели

Для `irreversible: true` сначала подготовить действие, озвучить его параметры и сохранить `pendingAction`. Исполнение допускается после отдельного явного согласия на **конкретное** ожидающее действие. Проверять и `requires_confirmation` сценария, и признаки действия.

Необратимые действия набора: `create_policy`, `renew_policy`, `update_policy`, `cancel_policy`, `create_claim`, `create_dispute`, `book_inspection`, `book_appointment`, `update_contact`.

Если параметры изменились, прежнее согласие не действует. «Да» без ожидающего подтверждения не разрешает изменение. Противоречие распознавания, особенно отрицание или цифры, требует уточнения. Дубликат события/повтор доставки не должен повторно изменять данные. Preview и execute — внутренние этапы исполнителя; не выдумывать, что в исходном контракте уже есть соответствующий API.

### Правила ответа

По README: 1–2 коротких предложения, один вопрос за раз, спокойный тон в срочных случаях и эмпатия при жалобе/страховом случае. Отвечать на преобладающем языке клиента и переключаться при его смене. Числа для речи представлять словами; при повторном озвучивании маскировать персональные данные. На вопрос «Вы робот?» отвечать честно.

`responses.opening` и `responses.closing` — ориентиры стиля, не универсальные записанные ответы. Факты берутся из базы знаний, найденных записей и результатов действий. Не генерировать внешние страховые правила.

### Передача оператору

Использовать очереди из набора и передавать краткое резюме: запрос, язык, найденный клиент, сценарии, собранные параметры, выполненные действия и причина перевода. Не заставлять клиента повторять весь разговор.

В этом MVP перевод, SMS, письма, оформление полиса и остальные внешние эффекты **симулируются**. Интерфейс и README явно сообщают это. Нет настоящей телефонии, денежных переводов и production-клиентов.

## 6. Голосовой контур TalkIt [КОМАНДА]

```text
                         ┌─ OpenAI STT + VAD ─┐
Микрофон → общий ход ─────┤                    ├─ DSR → согласованный текст
                         └─ Yandex SpeechKit ─┘                 │
Текстовый резерв ───────────────────────────────────────────────┤
                                                              ↓
                                                gpt-realtime / route_turn
                                                              ↓
                                                валидация + исполнитель
                                                              ↓
                                                текст ответа по данным
                                                              ↓
                                                     ElevenLabs V3
                                                              ↓
                                                      звук в браузере
```

- Переиспользовать только доступные и допустимые адаптеры. Не утверждать, что импорт работает, если исходники, ключи или тест подключения отсутствуют.
- Согласовать формат аудио и принадлежность сегментов одному ходу. Partial/final/refinement разных STT не должны порождать несколько бизнес-ходов.
- У одного `turnId` — одна финализация DSR и один окончательный запуск бизнес-обработки. Поздняя гипотеза не должна повторно исполнять уже принятое действие.
- Хранить обе гипотезы, выбранный текст, причину выбора, состояния провайдеров и неоднозначные поля. Не синтезировать отсутствующие цифры или отрицания, смешивая гипотезы без проверки.
- Ограниченное ожидание второго STT настраивать и измерять. Отказ одного провайдера показывать как деградацию, не как успешный DSR. При критичной неоднозначности переспросить.
- OpenAI не должен самостоятельно отвечать до согласования DSR. Изолировать речевой вход от контекста LLM-решения; простое отключение автоматического ответа не считать автоматически доказанной изоляцией уже полученного аудио.
- ElevenLabs V3 — единственный пользовательский TTS-путь. Не проигрывать параллельно голос OpenAI. Проверить реальные model ID, endpoint и транспорт существующего адаптера по актуальной документации; не подставлять V3 в случайный пример для другого режима.
- При остановке, новом ходе или сбросе сессии прекращать старое воспроизведение и игнорировать устаревшие чанки. Не допускать нескольких наложенных ответов.
- Обычный целевой ход: одно LLM-решение и одна генерация ответа по результатам исполнения. Не строить обязательную длинную цепочку отдельных агентов для языка, эмоций, каждого сценария и TTS.

Задержки, сравнение STT и DSR проверяются на фактических входах. Не заявлять, что DSR гарантированно лучше любого одиночного STT, без измерения. Отказ TTS не скрывать: текстовый ответ полезен для диагностики, но не закрывает обязательное голосовое требование.

## 7. Панель супервизора и измерения

### Обязательная трассировка [КЕЙС]

После каждой реплики показывать транскрипт, выбранные сценарии, понятное обоснование, альтернативы и время этапов. Отдельно обозначать неуверенность и ошибки.

### Дополнения нашей реализации [КОМАНДА]

Показывать гипотезы OpenAI/Yandex, результат DSR, активный и отложенные сценарии, безопасно отображённые слоты, вызванные действия и их результаты, ожидаемое подтверждение, handoff и состояние провайдеров. Добавить сброс сессии и экспорт трассировки без секретов.

Измерять этапы STT/DSR, маршрутизации, действий, подготовки ответа, TTS и фактического воспроизведения. **Сквозная задержка = начало воспроизведения ответа − конец речи клиента.** Первый байт на сервере не равен услышанному голосу. Приближённую оценку конца речи помечать как приближённую.

Не вычитать несинхронизированные часы сервера и браузера; использовать корректную корреляцию событий или отдельно показывать длительности. Не суммировать интервалы параллельных STT как последовательную задержку. Медиану считать по реальным валидным измерениям; число ошибок и отсутствующих измерений показывать отдельно, а не скрывать их.

Не считать пустую фразу-заполнитель содержательным ответом ради выигрыша таймера. Не рисовать в UI константу «500 ms» вместо замера.

## 9. Ограничения реализации

### Запреты задания [КЕЙС]

Не использовать готовый энкодерный intent-классификатор для выбора сценария; не подменять LLM-выбор хардкодом проверочных фраз; не строить единственный заранее записанный демонстрационный сценарий; не использовать реальные записи клиентских разговоров и реальные персональные данные во внешних API; не скрывать неуверенность; не выполнять необратимые действия без согласия.

### Границы пятичасового MVP [КОМАНДА]

Сохранить существующие Node.js, pnpm, TypeScript, H3, Vue/Vite и принятую в starter валидацию. Версии и импорты брать из реального lockfile/`AGENTS.md`, не обновлять всё на latest. Сохранять один существующий проект; не вводить новую платформенную архитектуру.

Не добавлять без необходимости отдельную БД, ORM, Redis, очереди, Kubernetes, SIP/АТС, настоящий CRM/страховой backend, векторную БД, универсальный SDK, сорок независимых агентов, редактор сценариев или обучение речевых моделей. Состояния процесса/сессии и mock-хранилища достаточно; ограничения сохранности описать честно.

Обычные unit-тесты и build должны запускаться без платных API-ключей. Живые интеграционные проверки — отдельно; отсутствие ключей показывается как «не проверено/недоступно», не как успешный реальный вызов.

Ключи только на сервере: не в `VITE_*`, Git, клиентском bundle, публичном журнале или экспортируемой трассировке. Не публиковать неограниченный прокси платных провайдеров. Для доступного deployment предусмотреть достаточные ограничения использования и безопасный способ доступа экспертов, не превращая это в разработку отдельной системы аккаунтов.

В ТЗ необязательны быстрый путь, потоковые оптимизации, эмоции, статистический dashboard и редактор каталога. При нехватке времени первыми исключать их и оформление. Не вырезать реальный голос, LLM-решение, русский/казахский, трассировку, подтверждения, обязательную сдачу и deployment.

Речевые адаптеры, браузерный UI и подготовку deployment проверять параллельно уже с первой функциональной фазой. Не обнаруживать невозможность удалённого запуска на последней минуте. Базовая трассировка должна появиться вместе с первым LLM-путём.

Владелец общих DTO, корневых конфигураций и lockfile — один интегратор. Другие агенты работают в согласованных областях. После каждой фазы отчитаться: что реализовано, какие файлы изменены, что реально проверено, что не проверено и какой критерий остаётся открытым. Не заменять исполнение очередным планом и не терять почасовое доказательство работы.

## 11. Финальная приёмка

### 11.1. Продукт и данные

- [ ] Произвольная русская фраза проходит микрофон → реальный STT → LLM → ответ по данным → слышимый TTS.
- [ ] То же проверено для казахского и смешанной речи; ответ на корректном языке.
- [ ] В маршрутизации доступны все 40 сценариев и 3 системных намерения.
- [ ] Проверены два намерения, уточнение, смена темы и продолжение разговора.
- [ ] Клиент найден по идентификатору; ответ использует его данные, не догадку о тестовом персонаже.
- [ ] Необратимое изменение без подтверждения невозможно; после подтверждения исполняется только ожидающее действие и не дублируется.
- [ ] Работают ошибка поиска, неизвестный запрос, явный запрос оператора и handoff с контекстом.
- [ ] Панель показывает действительные решения, альтернативы, причины, действия и задержки.
- [ ] Сброс сессии очищает контекст и mock-изменения; устаревший звук не воспроизводится.
- [ ] Симуляция, внешние зависимости и неподдержанные операции обозначены явно.

### 11.2. Проверки и сдача

- [ ] По lockfile выполнены доступные проверки типов, тесты и сборка; реальные результаты записаны.
- [ ] Сохранены предсказания по 104 репликам и вывод неизменённого `evaluate.py`.
- [ ] Проверены 10 многоходовых диалогов и отдельно живой голос; текстовый eval не выдан за голосовой тест.
- [ ] Есть проверенный deployment URL и безопасные данные доступа для экспертов.
- [ ] С другой машины/чистой сессии проверены страница, микрофон, STT, LLM, TTS и трассировка deployment, не только localhost.
- [ ] JSON-данные и необходимые зависимости доступны в развёрнутой сборке; API-ключи не утекли.
- [ ] README содержит предварительную настройку и одну реально проверенную команду запуска.
- [ ] В `docs/PREEXISTING.md` раскрыты ранее созданные и сторонние компоненты; вклад хакатона отделён.
- [ ] Есть реальное почасовое подтверждение прогресса и история в выданном репозитории.

Не отмечать пункты проверенными из предположения. При блокере записать конкретную причину, проверить независимые части и честно указать остаток. Недоступный голос или deployment — незакрытый обязательный результат, а не «готово с небольшими ограничениями».
