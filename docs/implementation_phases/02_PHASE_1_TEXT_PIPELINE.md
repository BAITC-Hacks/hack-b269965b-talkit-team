# Фаза 1 — настоящий текстовый сквозной путь

## Задание

1. Реализуй catalog.ts: загрузка и runtime-проверка исходных данных; проверка ссылок scenario → slot/action/system intent. Компактный промпт маршрутизатора генерируй из каталога: ID, description, not_this_if, priority и небольшой набор примеров ru/kk. Не вставляй mock_backend целиком и не читай expected-разметку в runtime.
2. Реализуй серверный адаптер gpt-realtime по фактическому используемому Realtime API. На вход текст, на выход текст/function call. Не обращайся к обычному REST endpoint в предположении, что любая модель поддерживается везде. Сначала проверь реальное соединение.
3. Зарегистрируй функцию route_turn с полями RouteDecision. В шаге маршрутизации запрашивай эту функцию, а не разговорный ответ. Дожидайся завершённых аргументов; проверь их JSON-парсером и Zod, существование ID и допустимость слотов. Не полагайся на Structured Outputs у gpt-realtime. Разреши не больше одной попытки исправить невалидный результат; затем честная ошибка или уточнение без действий. Ошибку транспорта не записывать как низкую уверенность клиента.
4. Сохраняй несколько намерений. Применяй not_this_if к каждой части, а не стирай одно намерение наличием другого. Порядок: urgent первым, остальные по порядку упоминания. Три системных намерения читать из исходного набора, а не придумывать.
5. Создай один handleTurn для текстового и будущего голосового ввода. Добавь создание/сброс in-memory сессии и POST /api/voice-router/turn. Endpoint сначала вызывается настоящим текстовым полем Vue; верни ответ, RouteDecision и trace. sessionId не подменяет идентификацию клиента.
6. Построй минимальный содержательный ответ: только выбранная карточка и подходящий фрагмент knowledge_base, без придуманных статусов/цен. При необходимости данных клиента — реальный вопрос об идентификаторе, а не выдуманный результат поиска. После валидированного маршрута подай разрешённый контекст gpt-realtime для короткого текста без tool calls.
7. Сразу сделай scripts/eval-router.mjs: читать dev_utterances только на стороне тестового runner, передавать маршрутизатору text с пустым состоянием, сохранять predictions.json формата исходного evaluate.py. Запросы разных примеров не должны видеть общую историю. Поля id/type/expected не должны попадать в промпт. Удобную команду pnpm run eval:router согласовать с владельцем package.json.
8. Сделай тесты схем, неизвестного ID, нескольких сценариев, невалидных аргументов и пустого ввода. Unit-тесты используют явно помеченный фейковый адаптер; live-eval отдельно и никогда не выдаётся за уже запущенный.

## Проверка

Через Vue введены новые, не зашитые в код фразы. Реальный gpt-realtime выбрал маршрут. На странице видны текст ответа, причины, альтернативы и измеренное время маршрутизации. Первый live-eval сохранён с фактической моделью и ошибками. При отсутствии ключа тестовый режим не выдаётся за конкурсную готовность.

## Не делать

До этого результата не строить подробный UI, идеальную архитектуру DSR и все 31 mock-действие.
