# Фаза 3 — разговор и mock-действия

## Задание

1. Сделай минимальное серверное состояние: идентифицированный клиент, язык ответа, активный сценарий, pending intents, стек прерванных сценариев, слоты, ожидаемый слот/подтверждение, история услышанных/прерванных ответов и consecutive unclear counter. Изолируй разные sessionId; данные для изменений клонируй на сессию. Сброс возвращает исходный mock-набор.
2. Используй общий исполнитель стадий: identification → collect slots → preview → confirmation → execute → completed/handoff. Это один механизм с небольшими правилами для сценариев, не 40 отдельных агентов. При срочном сценарии сначала следуй немедленной инструкции из базы знаний; не блокируй её длинным опросом/идентификацией.
3. Реализуй все action names из actions.json как синтетические обработчики, начиная с чтения: find_client, get_policy/get_policies, get_claim, kb_lookup, check_payment. Затем расчёты по knowledge_base, затем preview/execute изменяющих действий, затем журнальные моки SMS/callback/handoff. Не изменяй данные от чтения. Новые ID не должны пересекаться с имеющимися.
4. Не исполняй массив scenario.actions целиком на каждой реплике. Это не готовый исполняемый workflow. Явно определи шаги и зависимости аргументов; используй результаты предыдущих чтений. Запись A|B в inputs означает альтернативу идентификаторов, а не слот с таким буквальным именем. Для действий с неполными контрактами бери необходимые параметры из слотов сценария/диалогов; документируй принятые трактовки, не выдумывай бизнес-правила.
5. Поискать клиента и связанные полисы/случаи по предоставленным идентификаторам. Не брать первый клиент или первый полис автоматически. При нескольких подходящих объектах спросить какой. Не использовать скрытый client_id из dialogs_sample для заполнения живой сессии. Неизвестный телефон: следовать error_handling из actions.json, без вымышленного успеха.
6. Нормализуй слоты по slots.json; относительные даты по meta.as_of_date. Спрашивай один недостающий параметр за раз, используй уже известные значения и реальные профили. Не переспрашивай то, что достоверно известно.
7. Простое продолжение ожидаемого слота может заполнить состояние без полной повторной классификации; trace обязан показать унаследованный сценарий. Фразы «да, но…», смена темы, отказ и составные ответы не принимать слепо за подтверждение. При смене темы сохраняй текущий сценарий, обрабатывай новый и предлагай вернуться.
8. Защити необратимые действия на сервере: preview без мутации, pendingAction с ID и конкретными нормализованными аргументами, отдельное явное согласие пользователя, execute только для того же preview. Если параметры изменились, нужен новый preview и согласие. Повтор события/запроса с тем же pendingAction не создаёт вторую операцию. «Иә/да» без актуального pendingAction ничего не выполняет. После прерывания/смены темы не применять старое согласие к новому действию.
9. Реализуй policy thresholds из референсного README как конфиг приложения, не как научно подтверждённую вероятность. Для неуверенности — короткое уточнение; для повторной неуверенности и прямого запроса человека — handoff. Не считать provider timeout неуверенностью намерения. Передай в mock handoff язык, краткое резюме, активные/отложенные вопросы, найденные объекты и историю действий.
10. Генерируй ответ из выбранного сценария, слотов, результатов функций и фрагментов knowledge_base. На шаге ответа инструменты запрещены. Не зачитывай placeholders или статические closing без успеха действия. Одно-два коротких предложения, один вопрос, язык клиента. Ошибки и ограничения не маскировать «заявка оформлена».

## Проверка

Проверены: поиск/статус реального mock-клиента; несколько намерений без потери второго; смена темы и возврат; необратимое действие не меняет данные до согласия и выполняется один раз после; неизвестный идентификатор; передача человеку с контекстом. Пройти D03, D04, D07, D08 как ранний набор; затем все исходные диалоги.
