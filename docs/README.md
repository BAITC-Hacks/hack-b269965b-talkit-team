# Документация Voice Router

Этот каталог разделяет требования, план реализации, текущий статус, инструкции проверки и фактические свидетельства работы. Документы не заменяют исходный набор организатора и сами по себе не доказывают готовность функции.

## Быстрый маршрут чтения

### Перед первой работой в репозитории

1. [`../AGENTS.md`](../AGENTS.md) — обязательные правила проекта и технологические границы.
2. [`../README.md`](../README.md) — назначение, фактическая готовность, запуск и ограничения.
3. [`../TASK.md`](../TASK.md) — полные требования кейса, критерии и финальная приёмка.
4. [`STATUS.md`](STATUS.md) — последний короткий снимок состояния и следующий шаг.
5. [`compliance/PREEXISTING.md`](compliance/PREEXISTING.md) — граница starter, конкурсного вклада и внешних компонентов.
6. [`runbooks/VALIDATION.md`](runbooks/VALIDATION.md) — как запускать проверки и фиксировать результат.

При первичном разборе интегратор также читает исходные README и JSON в `data/voice-router/`. Для последующей локальной задачи достаточно перечитать затронутые требования, текущую фазу и относящиеся к ней данные.

## Текущий технический контекст

- Phase 0 присутствует в коде: набор данных, общие контракты, catalog loader, server-only конфигурация и baseline-тесты.
- Локальный текстовый путь включает HTTP turn/reset, `gpt-realtime`, структурированный tool call, валидацию, policy, состояние сессии и ответ по привязанным фактам.
- `App.vue` открывает Voice Router UI с голосовым звонком, резервным текстовым вводом и трассировкой.
- Browser PCM/WebSocket соединён с серверным WebSocket, OpenAI/Yandex STT, DSR и ElevenLabs V3 TTS. Живой браузерный звонок с провайдерами ещё не подтверждён.
- Есть eval runner, но нет подтверждённых live-метрик; mock-действия, полный диалог и публичный deployment не завершены.

Детали и доказательства не дублируются здесь: проверяйте `STATUS.md`, актуальный код и записи `progress/`.

## Источники истины

- `TASK.md` — требования и критерии приёмки. Метки `[ОРГ]`, `[КЕЙС]`, `[КИТ]`, `[КОМАНДА]` и `[САЙТ]` нельзя смешивать.
- `AGENTS.md` — исполнимые правила текущего репозитория.
- `package.json` и lockfile — фактические команды и версии.
- Исходники и тесты — фактически существующая реализация.
- `STATUS.md` — краткий текущий снимок, но не замена проверке кода.
- `progress/` — свидетельства конкретного запуска на конкретном состоянии; старый успешный отчёт не доказывает текущий checkout.
- `data/voice-router/README*.md` и JSON — исходный комплект задачи. Эти файлы сохраняются без редакторских изменений.

Каноническое техническое задание находится только в корневом `TASK.md`. Полную копию `docs/TASK.md` создавать не нужно.

## Как фиксировать выполненный шаг

После законченного изменения:

1. Запустить `pnpm run check`; перед контрольной точкой — `pnpm run verify`.
2. Добавить запись `progress/YYYY-MM-DD_HH-mm_<owner>_<topic>.md`.
3. Указать фактическое время и часовой пояс, цель, изменённые файлы, реальные команды и результаты, непроверенные пункты, ограничения и следующий шаг.
4. Обновить `STATUS.md` короткой ссылкой на запись.
5. Добавить commit/push только после их фактического выполнения; не придумывать SHA и доставку в remote.

Большие eval-результаты, predictions и обезличенные trace-артефакты при появлении хранятся в `artifacts/`, а в документации остаются краткое резюме и ссылка. Секреты, реальные клиентские данные и полные чувствительные логи не сохраняются.

## Важные границы

- Starter и ранее созданные речевые компоненты не являются конкурсным вкладом автоматически.
- `data/voice-router/` — синтетический исходный набор; его разметку и формулы нельзя менять ради метрик.
- Текстовый тест не подтверждает микрофон, DSR, TTS или end-to-end latency.
- Локальный smoke не подтверждает публичный deployment.
- Наличие `.env` или адаптера не подтверждает доступность внешнего API.
- Документ, commit или Markdown-запись не заменяет требуемую организатором процедуру почасовой фиксации и официальной сдачи.
